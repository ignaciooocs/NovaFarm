What each entity does

Hover over any box in the diagram to see this same summary in one line.

farms

The tenant: the farm the harvest is being tracked for. Everything else in the model belongs to exactly one farm — a farm never sees or reuses another's data. "Working independently" just creates a single-member farm; nobody is ever left without one.

users

The recorder (or admin) who uses the app. Logs in once with connectivity; the session is then saved on-device so workdays can be opened later without signal. nationalId is optional, same as on harvesters. workdays.recorderId is optional — you can also work as a guest, no account, within the device's active farm.

harvesters

The catalog of a farm's field workers, with identity persistent across workdays within that farm. The name isn't unique — the real identity is the _id — because two different people can legitimately share a name.

fruits

Catalog of products a farm can harvest (Lemon, Orange, Avocado...), owned by each farm. Editable at any time without touching code — adding a new fruit is just a piece of data, not a deploy.

measurementUnits

Catalog of containers or weighing methods (10kg Crate, 20kg Sack, Direct Kilos), each with its kg conversion factor. Lets the app switch between "container counting" and "direct weighing" without changing screens.

workdays

One day of harvest. Fixes the fruit and the day's default unit, and controls whether entries can still be recorded (OPEN) or totals are already frozen (CLOSED).

harvesterWorkday

The roster for a specific day: who worked that workday, with the local number that lets the recorder find them quickly on the list. Exists so someone shows up on screen even before they have a single entry recorded.

harvestEntries

Each individual delivery entry — the digital equivalent of a tally mark on the notebook. The highest-volume entity: every "+1" tap creates or increments a record here.

Full workday flow

From opening the day to uploading data to the server — which entity gets touched at each step.

1

Onboarding: role and farm (once, with connectivity)

Role first — "are you a recorder or an administrator?". If administrator, create a farm (for a team or independently, same action underneath). If recorder, enter an existing farm's invitation code. The session is saved on-device — from then on, opening the app and working doesn't depend on the network. You can also continue without an account, as a guest, within the device's active farm.

farms → create (admin) or validate invitationCode (recorder) users → authenticate, farmId assigned (or guest mode)
2

Open the workday

The recorder picks the date, the day's fruit, and the default container/unit (RF-01.1).

workdays → create, OPEN (recorderId or null if guest)
3

Build the roster

For each harvester who shows up at the station, search the catalog by name or create a new one if there's no clear match.

harvesters → search / create harvesterWorkday → create
4

Record each delivery

A "+1" tap (or +2, +5) adds units for that harvester; the system calculates kilos using the measurement unit's factor (RF-02.2, RF-02.3).

harvestEntries → create / increment measurementUnits → read kgFactor
5

Close the workday

At the end of the shift, the day's totals are computed once and frozen into the document itself (RF-01.2).

workdays → update, CLOSED
6

Sync

When there's signal, the recorder taps "Sync Workday" and everything captured locally uploads to the server (RF-04.3) — never before, never automatic.

workdays, harvesterWorkday, harvestEntries → syncedOffline: true

farmId lives on all 7 collections, not just 3

If workdays.farmId depended on recorderId → users.farmId, a guest workday (recorderId: null) would have no farm. That's why it's denormalized directly on every collection: it also spares every query from needing a $lookup just to filter by tenant — a forgotten join there is a data leak between farms, not just a bug.

harvesters is also scoped per farm

First name, last name, and national ID are personal data — a recorder at one farm shouldn't see or add another, unrelated farm's workers to their workday. Accepted cost: if someone works at two farms, each one registers them separately, with no shared history.

harvesterWorkday doesn't replace harvesters

harvesters is a farm's persistent catalog of people. harvesterWorkday is just the roster for a specific day — who worked that workday, independent of whether they already have an entry recorded.

workdayNumber is local, not global

Computed on the device itself (the workday's max + 1), with no dependency on the server or on syncing — that's why it works 100% offline.

The name isn't a unique key

A harvester's real identity is their _id. Two different people can share the exact same name, and the model tolerates that on purpose.

Login is only needed to sync

Recording in ui-app never depends on the network (RNF-01), so the session is saved locally after the first online login. The token is only needed when tapping "Sync Workday" — not to open the app or record harvests.

Guest mode doesn't block recording (but still has a farm)

workdays.recorderId is optional: without an account, the app keeps working the same way, just that data stays unattributed until that recorder logs in. Careful: this isn't the same as "no farm" — farmId is still set from the device, and is never null.
