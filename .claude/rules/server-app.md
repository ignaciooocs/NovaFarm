# server-app (NestJS) — conventions and current state

## Status

The full harvest-tracking vertical slice is implemented end-to-end — farms (create, plus `GET`/`PATCH /farms/me` for the caller's own farm settings and `POST /farms/me/invitation-code` to generate a new invitation code), auth (Firebase), products/harvesters/measurement-units catalogs (create/list/partial-update via `PATCH /:id`, the latter also doubling as activate/deactivate), a `users` controller (`GET /users` + `PATCH /users/:id/roles`), workdays (open/close), and the offline-sync endpoints (`POST /harvesters/sync`, `/harvester-workday/sync`, `/harvest-entries/sync` — all idempotent on a client-generated `clientEntryId`) — following the DTO/service/controller conventions below, plus a `/health` check and rate limiting on auth.

`AuthModule` imports both `UsersModule` and `FarmsModule` via `forwardRef()` (Auth needs both for registration; both now need Auth's guards for their own controllers) — a legitimate, NestJS-sanctioned pattern for a genuine two-way dependency, not something to "fix" by removing.

**Sync endpoints resolve their lookups per batch, not per item** (`POST /harvest-entries/sync`, since 2026-09-09): validate the workday once, then one query each for the already-synced `clientEntryId`s, the active harvesters in the batch, the workday roster, and the farm's unit catalog, and finish with a single `bulkWrite` of upserts keyed on the same unique index that made the old per-item `create()` idempotent. The per-item version cost ~5 sequential Atlas round trips per entry, so a full workday (98 entries) took longer than `ui-app`'s 15s HTTP timeout and the sync could never complete — a real bug found on device. `POST /harvester-workday/sync` and `POST /harvesters/sync` are still per-item (batches there are one row per person, an order of magnitude smaller); if either ever gets slow, this is the shape to copy.

**Anything that touches more than one entity in a single request gets logged start to finish.** `src/common/logging/sync-batch-log.ts` (`logSyncBatch`) prints one line per synced batch — scope, context, `recibidas/nuevas/ya/rechazadas`, the first rejection reason, and elapsed ms — and every sync service calls it on **every** exit path, rejections included. The HTTP middleware already says a request happened; this says what happened inside it, which is what you actually need when someone reports "entries stayed pending" from the field. Same vocabulary as `ui-app`'s `lib/syncLog.ts`, so the two halves read as one story. Keep it to one line, never the body, never PII.

A sync is 3-4 separate requests, and the server can't tell on its own that they're one run — so `ui-app` stamps every request of a run with the same `X-Sync-Id` header, and `src/common/context/request-context.ts` (plain `AsyncLocalStorage`, no dependency) carries it from the middleware down to any log line without threading it through service signatures. Both the HTTP line and `logSyncBatch` print it as `sync=<id>`, so `grep sync=3f9c2a` returns one whole sync in order even with several recorders uploading at once. The header is client text going into a log, so it's accepted only if it matches `^[A-Za-z0-9_-]{1,32}$` — a value with a newline in it could otherwise forge log lines. Use the same context for any future correlation id rather than adding a second mechanism.

The block is also **visually delimited**: `src/common/logging/sync-session-log.ts` prints a bold `══ sync <id> · INICIO ══` banner on the first request of a run and a `· FIN ·` one with the totals (requests, rows, rejections, elapsed) once 20s pass with no further request from that run — the device never says "I'm done", so idleness is the only honest end signal, and an unclosed block means the sync was cut. Simultaneous runs are tracked per id, so two recorders never share a block. Levels carry meaning: batch summaries are `log` (green), a batch with rejections is `warn` (yellow), and the HTTP line is `verbose` (cyan) so the request traffic recedes behind the business summary. Colors come from Nest's own level colors; the only manual ANSI is the banner's bold, and it's applied only when `process.stdout.isTTY` so log files and PaaS aggregators stay clean.

Known gaps: CI, e2e coverage beyond the scaffold test, and PaaS deployment aren't set up yet (see [arquitectura.md §3–5](../../docs/diagrams/arquitectura.md)).

## Errors: throw `AppException`, never Nest's own

Every business error throws `AppException` (`src/common/errors/app.exception.ts`) with a stable code from `src/common/errors/error-codes.ts` — `throw AppException.conflict('PRODUCT_NAME_TAKEN', 'A product with this name already exists for this farm')` — not `ConflictException` and friends. The code is what `ui-app` switches on to pick a Spanish message (`lib/errors.ts` there); the English text is for the log and Swagger and can be reworded freely. Matching the message was the old contract and it silently drifted, so don't reintroduce it. A global `AllExceptionsFilter` (`main.ts`) adds a generic code to everything that isn't an `AppException` (ValidationPipe, throttler, unmatched routes, unhandled 500s), so the shape `{ statusCode, code, message }` holds for every error response.

Adding an error means: a code in `error-codes.ts`, the throw, and its Spanish message in `ui-app/constants/strings.ts` + the map in `ui-app/lib/errors.ts`. Service specs assert the code (`rejects.toMatchObject({ code: 'WORKDAY_NOT_FOUND' })`), not the exception class — that's what keeps the contract honest. Full reasoning: [arquitectura.md §2](../../docs/diagrams/arquitectura.md).

**Still on the old contract:** the per-item `reason` strings in the sync responses (`harvest-entries`/`harvester-workday`) travel as English text and `ui-app` shows them verbatim to the field worker ("Workday is already closed"), which breaks RNF-02. Fixing it means a code field on those response DTOs plus an orval regen.

## Mongoose gotcha worth knowing

Adding a `required` field to an existing schema (`Workday.clientEntryId`, `Farm.recordersCanManageCatalog`) doesn't backfill it onto documents already in the database — a `.save()` on one of those old documents re-validates the *whole* document and throws (this broke `PATCH /workdays/:id/close` in practice). The fix pattern used throughout is `findOneAndUpdate` with a targeted `$set` (skips validation by default) instead of fetch-mutate-`.save()`, plus `?? <default>` in the service's `toDto()` for reads.

## Comment language

Identifiers, class names and DTO fields are English (see CLAUDE.md), but **code comments in `server-app` are written in Spanish**, and they explain *why* rather than restating the code — `products.service.ts` and `product.schema.ts` are the reference for the tone. Match that when editing existing files.

## Module boundaries

`server-app` is a modular monolith (one deployable, feature modules talking in-process via Nest DI — not microservices) — see [arquitectura.md §1](../../docs/diagrams/arquitectura.md) for why. One seam to watch: every entity module today exports raw `MongooseModule` (e.g. `FarmsModule`), which lets any importer bypass the owning module's business rules via direct `@InjectModel`. The intended convention going forward is each module exports its own `*Service` with purpose-built methods instead — cross-module reads/writes should go through that service, not a shared Mongoose model.

## Commands

```
pnpm start:dev   # dev server with watch mode
pnpm build        # nest build
pnpm lint          # eslint --fix
pnpm test           # jest unit tests
pnpm test:e2e        # jest e2e tests (test/*.e2e-spec.ts)
pnpm test -- <path>   # run a single test file
```

`server-app` needs a reachable MongoDB before `start:dev`/`start` finishes booting — `MongooseModule.forRootAsync` in `src/database/database.module.ts` blocks startup until it connects. Either set `MONGODB_URI_ATLAS` in `server-app/.env` (gitignored, see `.env.example`) and run `pnpm start:dev` on the host, or run `docker compose up` in `server-app/` — this builds the `dev` stage of `Dockerfile` (hot-reload via `nest start --watch`, source bind-mounted) alongside a local Mongo container, and always points at that local Mongo regardless of what `.env` has (never touches a real Atlas cluster). `server-app/Dockerfile` also has a `runtime` target (the default, used by `docker build .` with no `--target`) — a minimal multi-stage production image (no devDependencies, non-root user) for Railway/Render.

Watch mode (both bare `pnpm start:dev` and the `dev` Docker target) relies on `tsconfig.json`'s `watchOptions` (polling-based) — needed because native filesystem-change events don't reliably cross a Docker Desktop bind mount on Windows; don't remove it without confirming hot-reload still works inside the container.

After any DTO/controller change here, re-run `pnpm generate:api` in `ui-app/` (it reads this server's live OpenAPI spec) so the typed client stays in sync.

## Data model (MongoDB collections)

Adapted from the original relational DDL in REQUIREMENTS.md §4 — same business meaning, but referential integrity (`productId`, `harvesterId`, `measurementUnitId` references) is enforced at the application layer, not by the database. Entity/field names are English per the naming convention in CLAUDE.md (REQUIREMENTS.md still uses the original Spanish names — not yet updated). Full diagram and rationale: [docs/diagrams/modelo-datos.md](../../docs/diagrams/modelo-datos.md).

- `farms` — `{ _id, name, type: 'organization'|'independent', invitationCode, active, createdAt }` — the tenant. Every other collection carries a `farmId` and belongs to exactly one farm; no cross-farm data access. No `adminId` field — a farm's admin(s) are derived via `users` where `farmId` matches and `role: 'admin'`. `invitationCode` is what a `recorder` enters during onboarding to join, and it **expires one hour after it is generated** (`invitationCodeExpiresAt`, 2026-09-20): `POST /farms/me/invitation-code` (admin only) generates a new one and invalidates the previous immediately, and `isInvitationCodeExpired()` treats a missing expiry (farms created before this) as expired. Joining with an expired code is a 410, deliberately distinct from the 404 of a code that doesn't exist. `type` is UI-only (whether to show the "invite your team" step after creation), no backend logic differs.
- `users` — `{ _id, farmId, name, email, firebaseUid, nationalId?, roles: Array<'recorder'|'admin'|'supervisor'>, active }` — authenticated users of `ui-app`. **`roles` is an array** (multi-role, 2026-09-04): one account can hold several at once (e.g. an admin who also records), `RolesGuard` authorizes on *any* match, and which role is "active" is local-only device state in `ui-app` (never round-tripped through the server). `PATCH /users/:id/roles` reassigns the recorder/supervisor set; it can never grant or revoke `'admin'` itself, and if the target already is an admin that role is preserved and only the extras change. Auth is delegated to **Firebase Authentication**: `ui-app` logs in directly against Firebase's client SDK, `server-app` never handles a password and only verifies the resulting ID token via `firebase-admin`, with `farmId`/`roles` carried as custom claims on that token; `firebaseUid` links the document back to the Firebase user. `farmId` is **required, never null** — "working independently" auto-creates a 1-member farm rather than leaving a user tenant-less (this is a different concern than `workdays.recorderId` being nullable: that's about attribution, this is about data isolation — a null farmId risks two users seeing each other's data). Login requires connectivity once; the session/token is then persisted locally on-device (refreshed in the background by the Firebase SDK) and only re-checked at sync time — local capture (RNF-01) never depends on it. Onboarding order: ask role first (recorder/admin), then affiliation — admin creates a farm (labeled either "for my team" or "independent", same backend action, differs only in `type` and post-creation UI); recorder joins an existing farm via `invitationCode`. There is no "independent recorder" path — working alone still requires admin-level catalog control.
- `harvesters` — `{ _id, farmId, firstName, lastName, nickname?, nationalId?, active }` — persistent worker catalog, **scoped per farm** (not global — a farm's roster, including PII like `nationalId`, must not be visible to another farm). `firstName`+`lastName` is **not** a uniqueness key — two different people can share a name; identity is `_id`. `nationalId` is optional/nullable (not collected at quick field registration, filled in later by an admin). `nickname` is optional and exists to help disambiguate repeated names.
- `products` — `{ _id, name, icon, source: 'APP'|'COMMUNITY', createdByFarmId?, catalogKey?, featured, active }` — the crops themselves, and **the one collection in the model without a `farmId`**: there is a single "Palta" row shared by every farm, not a copy per farm. That sharing is the whole point — it makes `GROUP BY productId` across every farm's workdays mean something, which grouping by text never could. It doesn't weaken tenant isolation because it isn't tenant data: what each farm grows lives in `farmProducts` below, which does carry `farmId`.
  - `source: 'APP'` — shipped by the app, seeded on boot from `product-catalog.ts` (a code constant; `ProductsService.seedCatalog` upserts by `catalogKey`, so it's idempotent and adding an entry publishes it to everyone on the next deploy). Visible to every farm.
  - `source: 'COMMUNITY'` — created by a farm because the catalog didn't cover it, and **visible only to that farm** (`createdByFarmId`) until it's promoted to `APP`. The isolation isn't tenant paranoia: without it the first typo anyone makes ("palta", "Palta Hass", "PALTA") shows up in everyone's picker and splits the very metric this collection exists to enable. Promotion has no endpoint yet — it's a manual flip of `source`/`createdByFarmId`.
  - Unique index `{ name, createdByFarmId }` covers both cases at once: `APP` rows (null owner) are unique globally, a farm's own rows are unique within that farm. This is what keeps "adding a product must not require code changes" (CLAUDE.md) true — the catalog is a shortcut, not the only door.
- `farmProducts` — `{ _id, farmId, productId, active }` — which products a farm grows; the direct replacement for the old per-farm `fruits` collection, which conflated the crop with the fact that this farm harvests it. `active` belongs to the *selection*: a farm that stops growing avocado deactivates it here without touching anything global or losing past workdays.

  `ProductDto.editable` says whether name/icon can still change, and it's only ever true for a `COMMUNITY` product **this** farm created that **no workday uses yet**. An `APP` product's labels belong to the app; and renaming a used product would silently rewrite what past workdays say was harvested, since history resolves name and icon *live* against `products` (nothing is snapshotted into `workdays`). `ProductsModule` registers the `Workday` model directly for that in-use check — going through `WorkdaysModule` would close a cycle, same reason and same fix as `HarvestEntry` in `workdays.module.ts`.
- `measurementUnits` — `{ _id, farmId, name, mode: 'COUNT'|'WEIGHT', kgFactor?, active }` — `mode` says how a delivery made with this unit is captured, and it's **explicit, never inferred**: `COUNT` is a fixed-weight container (a 20kg tarro) where the recorder counts containers and kilos come from `kgFactor` (10kg crate → 10.000); `WEIGHT` is a container weighed on every round (a capacho) where each entry is one container and the kilos come from the scale, so `kgFactor` is null. Before `mode` existed this was inferred from `kgFactor === 1`, which forced admins to invent units like "capacho 1kg" and made `unitCount` mean kilos for those — don't reintroduce that sentinel. `toDto()` still applies it as a fallback for any document written before the field existed. Scoped per farm — unlike `products`, a unit is genuinely per-farm (each names its own containers).
- `workdays` — `{ _id, farmId, date, productId, defaultMeasurementUnitId, status: 'OPEN'|'CLOSED', createdAt, finalTotalKg, recorderId?, payRate?, payBasis? }` — closing a workday (RF-01.2) should compute and freeze aggregate totals into the document itself rather than recomputing via aggregation on every read. `recorderId` is set to **whoever opens the workday, whatever their roles** (2026-09-20 — it used to need the `recorder` role, and an admin's workday stayed unattributed, which made it unrecoverable on another device); it stays nullable for the guest-mode workdays opened before that. `farmId` is **never** null even then; it's set from the device/session's active farm at workday-creation time, independent of `recorderId`. Don't derive `farmId` transitively via `recorderId → users.farmId` — that path breaks precisely for guest-mode workdays. `payRate` (whole CLP, a plain `Number` — pesos have no cents, so there's no drift to guard against) and `payBasis` (`'PER_UNIT'|'PER_KG'`) are what a harvester earns per container or per kilo that day; both are **optional and set together or not at all**, and `PER_UNIT` is rejected for a `WEIGHT` unit (paying per weighed container = paying per trip). They live on the workday, not on the unit, because the price follows the crop and the day, not the container. Per-harvester amounts are always derived from `harvestEntries`, never stored. `PATCH /workdays/:id/pay` corrects the rate while the workday is `OPEN` and refuses once it's `CLOSED` (409), same reasoning that freezes `finalTotalKg`.
- `harvesterWorkday` — `{ _id, farmId, workdayId, harvesterId, workdayNumber, addedAt, syncedOffline }` — the day's roster (which harvesters are working that workday), decoupled from `harvestEntries` so someone shows up in the recorder's list before their first delivery. `workdayNumber` is a per-workday correlative (1, 2, 3...) assigned locally on-device (not a server-issued global sequence) so it works fully offline — unique per `workdayId`, never a global worker ID. `farmId` is denormalized from the workday (cheap — already in memory on-device) so tenant-filtered queries never need a `$lookup`.
- `harvestEntries` — `{ _id, farmId, workdayId, harvesterId, measurementUnitId, unitCount, totalKg, measuredKg?, recordedAt, syncedOffline }` — `unitCount` is **always a whole number of containers, never kilos**, whatever the unit's mode (in `WEIGHT` it's 1, or -1 for a correction); kilos live only in `totalKg`, which the server always resolves itself (`unitCount × kgFactor` for `COUNT`, the client's `weightKg` for `WEIGHT`) and rounds to one decimal — the whole system's resolution, enforced at the DTO level with `maxDecimalPlaces: 1`. References `harvesterId`+`workdayId` directly (not via `harvesterWorkday._id`) to avoid an extra lookup in the local write hot path. `farmId` denormalized for the same reason as above — this is the highest-volume collection in the system, so every query here needs tenant scoping without a join. `measuredKg` is an **optional control weight for `COUNT` units only** (the catalog says the tray is 3.0 kg, someone recorded that this one really weighed 3.4): it never enters `totalKg` and never enters the pay — if the real weight is meant to drive the money, that's a `WEIGHT` unit — and it's rejected outright for `WEIGHT` units, where the scale reading already is `totalKg`. Don't confuse it with the sync DTO's `weightKg`, which is the scale reading for a `WEIGHT` unit and becomes `totalKg` instead of being stored. It is also the **only** field a re-sync may overwrite on an already-synced entry (a round often gets weighed after the fact); `unitCount`/`totalKg` stay immutable, which is what that rule protects.

## API layer

`main.ts` wires three things globally rather than per-controller: a `ValidationPipe` (`whitelist`, `transform`, `forbidNonWhitelisted` — a client can't smuggle in a server-assigned field, e.g. `farms.invitationCode`); a global `api/v1` prefix (`app.setGlobalPrefix('api/v1', { exclude: ['health'] })`, per [arquitectura.md §2](../../docs/diagrams/arquitectura.md)) so every controller route is served under `/api/v1/...` except `/health` (kept stable and unprefixed since it's an infrastructure check, not part of the versioned contract); and `@nestjs/swagger`, which auto-documents any DTO decorated with `@ApiProperty()` at `/api-docs` (mounted only when `NODE_ENV !== 'production'`, and itself unaffected by the prefix since it mounts on the underlying HTTP adapter directly).

## DTO structure

Every entity module owns a `dto/` folder, structured by direction first, then by action — only create the files an implemented endpoint actually needs, don't pre-generate the full set. `server-app/src/farms/` is a working reference implementation of this structure end to end (schema → DTOs → service → controller) — copy its shape for the next module rather than re-deriving it:

```
src/<entity>/
  dto/
    request/
      create-<entity>-request.dto.ts        # export class Create<Entity>RequestDto
      find-<entity>-request.dto.ts          # export class Find<Entity>RequestDto
      find-by-id-<entity>-request.dto.ts    # export class FindById<Entity>RequestDto
    response/
      create-<entity>-response.dto.ts       # export class Create<Entity>ResponseDto
      find-<entity>-response.dto.ts         # export class Find<Entity>ResponseDto
      find-by-id-<entity>-response.dto.ts   # export class FindById<Entity>ResponseDto
    types/                                   # optional — only if the module needs a standalone type/interface that doesn't fit the entity/request/response split
    <entity>.dto.ts                          # export class <Entity>Dto — the entity's canonical shape
    index.ts                                 # barrel — re-exports everything under dto/
  schemas/<entity>.schema.ts
  <entity>.module.ts
```

Rules:
- One DTO class per file. The filename is kebab-case and matches the exported class name 1:1 (e.g. `create-farm-response.dto.ts` exports `CreateFarmResponseDto`).
- Split by direction first (`request/` = what the client sends, `response/` = what the endpoint returns), then by action inside each (`create`, `find`, `find-by-id`, `update`, ...), mirroring the controller's operations.
- `<entity>.dto.ts` (e.g. `farm.dto.ts` → `FarmDto`) is the module's canonical DTO: the entity's shape independent of any specific action. Request/response DTOs for individual actions are typed against it (extend or compose from `<Entity>Dto`) instead of re-declaring the same fields and `class-validator` decorators per action — a field added to the entity's shape shouldn't require hunting down every action's DTO separately.
- `types/` is optional — add it only when a module needs a standalone type/interface that isn't itself a request, a response, or the entity shape.
- Other layers (controller, service, other modules) import from `<entity>/dto` (the barrel), never by reaching into `dto/response/...` or `dto/request/...` directly.

## Multi-tenant isolation — enforcement mechanism

Multi-tenant isolation is non-negotiable (see CLAUDE.md): every collection carries `farmId`, and every query must filter by it directly — never rely on a transitive join (e.g. through `recorderId`) to scope by tenant, since nullable fields like `workdays.recorderId` (guest mode) break that path. A forgotten `farmId` filter is a cross-tenant data leak, not just a bug.

Identity is handled by **Firebase Authentication**, not a homegrown JWT — `ui-app` signs up/in directly against Firebase (client-side, via the `firebase/auth` SDK), and login never passes through `server-app`. `server-app` only verifies the Firebase ID token the client presents, via `firebase-admin` (`src/auth/firebase-admin.service.ts`); `farmId`/`roles` travel as custom claims set on the Firebase user at the end of registration (`admin.auth().setCustomUserClaims`) — note the claim is the array, and it's what `RolesGuard` actually reads on every request, so any change to a user's roles has to update both the Mongo document and the claim or it has no real effect. A `FarmScopeGuard` (`src/auth/guards/farm-scope.guard.ts`) verifies the token and requires those claims to be present, and a `@CurrentFarm()` param decorator (`src/auth/decorators/current-farm.decorator.ts`) reads `farmId` off the request it populates — both live in `src/auth/` and are exported from `AuthModule` for reuse by other modules.

Applied via `@UseGuards(FarmScopeGuard)` on every entity controller that reads/writes tenant data — `products`, `harvesters`, `measurement-units`, `workdays`, `harvester-workday`, `harvest-entries`, `users` — so any new entity controller should follow the same pattern. `farms.controller.ts` is the deliberate exception (no guard): its one route creates the tenant itself, before a `farmId` claim can exist. For routes that also need to restrict *which* farm member can call them (not just that they belong to a farm), pair `FarmScopeGuard` with `RolesGuard` (`src/auth/guards/roles.guard.ts`) + `@Roles('admin')` — used across `users.controller.ts` (class-level `@Roles('admin')`, with `/me` routes and `GET /users` overriding it at the method level) and `PATCH /farms/me`; everything else is reachable by any authenticated farm member regardless of role. `@Roles()` lists the roles that are *enough*, and the guard passes if the caller holds any one of them.
